# Phase 2 Spec — Upload Safety, Render Sandbox, Layout Gate, Onboarding

Written by Opus for the implementing model. Read it all before writing code.
Phase 1 (`PHASE1_SPEC.md`) still applies; this file adds to it. Every rule
below was checked against the 9-resume corpus and the fixtures in
`fixtures/phase2/` (generated by `tools/make_phase2_fixtures.py`).

---

## 0. Decisions (made; don't revisit)

| # | Decision |
|---|---|
| P1 | An upload with tracked changes is **rejected** ("accept or reject your changes in Word first"). Never auto-accepted. |
| P2 | Fewer than **3** editable bullets after locking → **rejected**. |
| P3 | Fonts outside the Phase 1 map get **family-based candidates** (serif/sans/mono), shown in the preview. Rejected only if no candidate lets the resume fit. |
| P4 | Bullets containing a hyperlink stay **locked** in v1 (so do tab, field, line-break bullets — Phase 1 section 4.4). |
| P5 | Upload size cap: **2 MB**. |
| P6 | Target page count = the resume's own page count after normalization, **capped at 2**, with the spill rule in 4.1. |

Two principles:

1. **LibreOffice only renders files we wrote.** Every upload is checked, then
   re-saved by `DocxPackage` before anything renders it. A crafted zip that
   reads differently to different parsers never reaches LibreOffice as-is.
2. **Lock, don't reject**, whenever a problem affects one bullet. Reject only
   for unsafe files or when too little stays editable.

## 2. Step 2.1 — Upload gate

`UploadGate.check(byte[] upload) -> GateResult` runs **before** anything else
and **never renders**. Checks run in this order; the first failure wins and
names its reason. Every fixture in `fixtures/phase2/` trips exactly one check,
so the order matters.

| # | Check | Limit | Reason code |
|---|---|---|---|
| 1 | Upload size | > 2 MB | `FILE_TOO_LARGE` |
| 2 | Starts with `D0 CF 11 E0 A1 B1 1A E1` (OLE: encrypted .docx or legacy .doc) | — | `ENCRYPTED_OR_LEGACY` |
| 3 | Not a readable zip | — | `NOT_A_DOCX` |
| 4 | Entry count (central directory) | > 200 | `TOO_MANY_ENTRIES` |
| 5 | Two entries with the same name | — | `DUPLICATE_ENTRY` |
| 6 | Unsafe entry name: empty, starts with `/` or `\`, contains `\`, a drive letter (`C:`), or any `.`/`..` path segment | — | `UNSAFE_PATH` |
| 7 | Declared total unpacked > 20 MB, any entry > 10 MB, or any entry's size/compressed > 200 | — | `ZIP_BOMB` |
| 8 | Missing `[Content_Types].xml` or `word/document.xml` | — | `NOT_A_DOCX` |
| 9 | Any entry ending `vbaProject.bin` (case-insensitive), or content types containing `macroEnabled` | — | `MACROS` |
| 10 | Any entry under `word/embeddings/` or `word/activeX/` | — | `EMBEDDED_OBJECT` |
| 11 | Any relationship with `TargetMode="External"` whose type is **not** hyperlink | — | `EXTERNAL_RESOURCE` |
| 12 | Every `.xml` / `.rels` part must parse with SafeXml: no DOCTYPE, no entities, element depth ≤ 100 | — | `UNSAFE_XML` |
| 13 | `word/document.xml` contains `w:ins`, `w:del`, `w:moveFrom` or `w:moveTo` | — | `TRACKED_CHANGES` |

Corpus measurements behind the limits: max 16 entries, max 583 KB unpacked,
max ratio 40 (Subodh). All 9 corpus resumes pass the gate; the Python
reference (`reference/gate_ref.py`) reproduces every fixture's expected
reason.

### 2.1.1 Implementation rules

- **Declared sizes can lie.** Check 7 uses the central directory, but reading
  must also enforce the limits on the bytes actually inflated: stop and return
  `ZIP_BOMB` the moment an entry passes 10 MB or the running total passes 20 MB.
- **Switch `DocxPackage.open` to the central directory** (`java.util.zip.ZipFile`
  on a temp copy, or equivalent), not `ZipInputStream`. LibreOffice reads the
  central directory; so must we, so we check the same entries it would see.
  `DocxPackage.open(Path)` must go through the gate's limits; add
  `DocxPackage.fromGatedUpload(...)` or have the gate return the parts.
- If Java's zip reader itself throws on a duplicate name, map that to
  `DUPLICATE_ENTRY`, not a crash.
- **Depth limit:** set `jdk.xml.maxElementDepth` on the SafeXml factory
  (`factory.setAttribute("http://www.oracle.com/xml/jaxp/properties/maxElementDepth", "100")`)
  and verify it with `deep_nesting.docx`. If the attribute isn't honored,
  count depth with a SAX pre-pass instead.
- **Remove recursion** from `BodyWalker.walkRecursive` and
  `DomUtil.descendants/containsDescendant` (explicit stack). The depth limit
  protects them today; this makes them safe if someone later bypasses the gate.
- Font normalization rewrites XML with regex. It must only ever see parts that
  already passed check 12.
- A rejection costs **zero renders** (test P2-T1 counts them).

### 2.1.2 Messages shown to the user

| Reason | Message |
|---|---|
| `FILE_TOO_LARGE` | Your file is over 2 MB. Save it without embedded images or fonts and try again. |
| `ENCRYPTED_OR_LEGACY` | This file is password-protected or in the old .doc format. Remove the password or save it as .docx. |
| `NOT_A_DOCX` | This doesn't look like a Word .docx file. |
| `TOO_MANY_ENTRIES`, `DUPLICATE_ENTRY`, `UNSAFE_PATH`, `ZIP_BOMB`, `UNSAFE_XML` | We couldn't safely read this file. Try saving it again from Word as a new .docx. |
| `MACROS` | This file contains macros. Save it as a plain .docx (not .docm) and try again. |
| `EMBEDDED_OBJECT` | This file contains embedded objects. Remove them and try again. |
| `EXTERNAL_RESOURCE` | This file loads content from the internet (for example a linked image). Insert the image directly and try again. |
| `TRACKED_CHANGES` | Your resume has tracked changes. Accept or reject them in Word, then upload again. |
| `TOO_MANY_PAGES` | Resumes longer than 2 pages aren't supported yet. |
| `TOO_FEW_EDITABLE` | We could only find {n} bullet points we can safely edit. Tailoring needs at least 3. |
| `NEEDS_USER` | Your resume doesn't fit on {n} page(s) with our fonts. (Preview offers options.) |

## 3. Step 2.2 — Render sandbox

Phase 2 runs the engine in a restricted container. Add a runtime image (or a
runtime stage in the Dockerfile) that:

- builds the CLI fat jar at image build time (`gradle :cli:jar`);
- runs as a non-root user (`variant`);
- keeps the LibreOffice profile and all work files under `/tmp`.

Run it with:

```
docker run --rm --network none --read-only --tmpfs /tmp:rw,size=512m \
  --memory 1g --cpus 1 --pids-limit 256 --cap-drop ALL \
  --security-opt no-new-privileges \
  -v <input dir>:/in:ro -v <output dir>:/out \
  variant-runtime java -jar /app/tailor.jar onboard /in/resume.docx /out
```

Acceptance: all 9 corpus resumes onboard successfully inside this sandbox, and
`curl https://example.com` fails inside it. The 60 s render timeout and one
retry from Phase 1 stay.

Gradle-based testing stays in the existing dev image; the sandbox is for
running uploads, not for building.

## 4. Step 2.3 — Layout gate

Runs after font normalization, on the normalized file.

### 4.1 Page rule (P6)

1. Normalize fonts (Phase 1 section 3, plus 4.3 below) and render. Pages = `P`.
2. **Spill rule:** if `P > 1` and the last page holds **5 lines or fewer**,
   it's a spill. Try the shrink steps (0.5 pt, 1.0 pt) to reach `P − 1`.
   Measured: the 3 converted resumes spill 3, 2 and 1 lines and all pull back
   to 1 page at 0.5 pt, matching golden `shrink_pt`. Real second pages hold
   far more (the too-many-pages fixture: 17 lines on its last page).
3. Target = resulting page count. If it's > 2 → `TOO_MANY_PAGES`.
4. If shrink can't pull a spill back, accept at `P` pages (≤ 2) and say so in
   the report; the user confirms in the preview.

This replaces Phase 1's fixed `--target-pages 1`. On the corpus it produces
exactly the same pages and shrink values as golden.

### 4.2 Locking

A supported bullet becomes **locked** (visible, never edited) if:

- it has an unsupported reason (Phase 1 4.4: `hyperlink`, `line_break`,
  `tab_in_text`, `field`, `tracked_change`) → lock reason is that code; or
- **shared lines**: in the normalized render, its text can't be anchored, or
  its anchored lines contain text other than its own (ignoring the bullet
  glyph) → lock reason `shared_lines`. This catches bullets side by side in
  columns, next to a sidebar, or beside a text box, without trying to guess
  layout roles from the XML.

Measured: all 130 corpus bullets anchor with no foreign text. The
`side_by_side.docx` fixture (two bullets forced into neighbouring columns)
locks exactly those two; the bullets around them stay editable.

After locking: editable < 3 → `TOO_FEW_EDITABLE` (P2).

### 4.3 Unknown fonts (P3)

A font is unknown if it's named in the document (run/style/theme font
attributes) but is neither a key nor a value of the font map and isn't a glyph
font (`Symbol`, `Wingdings*`). For each unknown font:

1. Read its family from `word/fontTable.xml` (`<w:font w:name="…"><w:family w:val="…"/>`).
2. Candidates by family:
   - `roman` → Liberation Serif, Caladea, Gelasio RT, TeX Gyre Pagella
   - `swiss` → Liberation Sans, Carlito, DejaVu Sans
   - `modern` → Liberation Mono
   - missing/other → the `swiss` list
3. Use the first candidate; run the page rule. If it's rejected for pages, try
   the next candidate. If none fits → `NEEDS_USER`.
4. Record every substitution in the report, marking whether it's
   metric-compatible (only Phase 1 map pairs are).

Measured: `unknown_font.docx` (Constantia, family roman) renders in Liberation
Serif on 1 page and passes the font audit.

## 5. Step 2.4 — `tailor onboard`

```
tailor onboard <upload.docx> <outDir> [--skip-calibration]
```

Pipeline: gate (2.1) → normalize (Phase 1 §3 + 4.3) → page rule (4.1) →
detect → lock (4.2) → min-editable check → calibrate hints (Phase 1 §7.3) →
write outputs.

Outputs in `outDir`:

- `normalized.docx` — the file every later step starts from
- `preview.pdf` — its render, for the user to approve
- `onboard.json`:

```json
{
  "accepted": true,
  "reason": null,
  "message": null,
  "pages": 1,
  "shrinkPt": 0.5,
  "squeezeRemoved": 759,
  "positionRemoved": 0,
  "fonts": [{"from": "Georgia", "to": "Gelasio RT", "metricCompatible": true}],
  "editableCount": 14,
  "slots": [
    {"index": 0, "text": "…", "lines": 2, "editable": true, "lockReason": null, "hintChars": 187}
  ],
  "rendererVersion": "24.2.7.2"
}
```

Rejected uploads write only `onboard.json` with `accepted: false`, the reason
code, and the user message from 2.1.2.

## 7. Build order

1. **2.1a** Harden `SafeXml` (depth) and remove recursion (P2-T6).
2. **2.1b** `UploadGate` + `DocxPackage` via central directory (P2-T1).
3. **2.3** Page rule, unknown fonts, locking (P2-T2, P2-T3).
4. **2.4** `tailor onboard` (P2-T4, P2-T5).
5. **2.2** Runtime image and sandbox run (P2-T7).

After step 2 (the gate), stop and ask for an **Opus security review** before
continuing.

## 8. When to stop and escalate to Opus

- Any corpus resume is rejected, or any corpus bullet gets locked.
- A fixture trips a different check than `expected.json` says.
- You're tempted to raise a limit, reorder checks, or special-case a file to
  make a test pass.
- The depth limit or duplicate-entry detection doesn't behave as described.
